# Changelog

## Unreleased (BREAKING)

- Reason parity: a capability hop whose body the strict profile cannot canonicalise (e.g. a caveat number outside the safe range) is refused with `hop N: malformed body` like the reference, instead of the generic `malformed capability chain: JsonError` backstop.
- ML-DSA discovery: `ATLAS_PCA_LIBCRYPTO` may list several libcrypto paths separated by `PATH_SEPARATOR` (tried in order; a library without ML-DSA is skipped). The redundant OpenSSL version-number gate is gone: the capability probe (building an ML-DSA-65 key) is the test.

- R6-05 follow-up (robustness): `verifyChain` and `caveatLimitExceeded` take ANY JSON value (`mixed`, was `array`): a chain that is not a JSON array is refused as the empty chain like the reference, instead of a `TypeError` escaping. `signerSetHashRaw` returns null (fail-closed, as documented) for a set whose role / key / `pq_pk` strings the strict profile refuses (e.g. a lone surrogate) instead of throwing `JsonError`. Depth: the strict profile and canonical form refuse nesting past 32 (outermost container = 1, as in the reference); the lax loader stops at 512; tests at 31/32/33 and far beyond.

- R6-03/R6-04 (parity): `verifyThresholdShare` validates the WHOLE signer set like the reference: unknown or wrong-case roles, malformed keys, and an empty / null / short / non-canonical `pq_pk` anywhere in the set refuse it; one key per role, one role per key; a duplicate (role, key) entry only with the same `pq_pk`. `share.role` is required. `t` accepts an integral number 1, 2 or 3 (also `1.0`). `signerSetHashRaw` hashes any string set (UTF-8 byte order); key validity is checked by the registry.
- R6-05 (robustness): `verifyChain`, `verifyJson` and `verifyPcactnCore` are total (a malformed input is a verdict, never a `\Throwable`); the per-hop type check mirrors the reference `wellTyped` (string id/issuer/holder/body_digest/sig, optional alg/pq_pk/pq_sig/holder_pq/parent strings, caveats a list of objects with a string `type`). Correctly SIGNED hops with ill-typed caveats, holder or holder_pq were accepted before, and a hop with a numeric `pq_pk` was accepted.
- R6-02 (security): a signer-set role that registers a `pq_pk` now REQUIRES a PQ (pure or hybrid) threshold share; an ed25519-only share for that role is refused, so an Ed25519 break no longer forges a hybrid-registered role (parity with the TypeScript reference). Corpus: `agent-bound-signerset-with-pq-pk` is now `valid:false`; new positive `agent-hybrid-signerset-with-pq-pk`.
- R5-A1 (security): threshold-share verification is now signer-set PINNED, no longer self-vouched. The share must be for the one key the signer set registers for its role, a PQ/hybrid share verifies only under the set's registered `pq_pk` (a differing share `pq_pk` is refused), the share-suite tag is part of the signed bytes (a classical share cannot be relabelled hybrid), and the signer-set hash now includes a registered `pq_pk` (parity with the TypeScript reference). New corpus vectors: `agent-not-in-signer-set`, `agent-bound-signerset-with-pq-pk`, `agent-hybrid-relabel-*`.

- Suite policy defaults documented: no list = no restriction, an empty list refuses everything, and the hosted API defaults to ed25519 + Ed25519 hybrids (README lists the exact list to pass offline).

- R4-01: `Pca::verifyChain` now takes the root's PQ authority from the verifier, exactly like the TypeScript reference (R3-01). Two new trailing arguments, `$pqPins` (`Obj` or `array<string,string>`: root issuer Ed25519 b64u => PQ public key) and `?Obj $trustedRoot` (the verifier's own stored root capability). A non-ed25519 (pure `ml-dsa-65` or hybrid) ROOT hop is accepted only if `$pqPins[root.issuer]` equals the root's `pq_pk`, or `$trustedRoot` is the root itself (same content hash). Otherwise it is refused with `hop 0: root suite '<alg>' needs a PQ key pinned for the root issuer (policy.pqPins) or the verifier's stored grant (policy.trustedRoot); the root's own pq_pk proves nothing about who issued it (R3-01)`. Before, a pure-PQ root signed with the attacker's own ML-DSA key but naming a victim Ed25519 issuer verified. Callers of `verifyChain` on a root they did not load from their own store must now pass `$pqPins`. `verifyPcactnCore` / `verifyJson` are unchanged in behaviour (they pass the grant as `$trustedRoot`). Internally one `resolvePqKey` choke point mints the only key type (`PinnedPq`) that `verifySuite` accepts, so the PQ verify cannot be called with an artifact key.
