# Changelog

## Unreleased (0.5.0)

- **Breaking** (default): `PcaMiddleware` now runs the full `Authorize::authorize` pipeline by default. Without an `AuthorizeOptions` the option set is empty and every request is refused with a 403 `authorize_config` whose `missing` list names the absent components (`stateStore`, `isRevoked`; then `operation`). Verifying the signature and chain only is now the explicit opt-in `signatureOnly: true`; passing it together with `authorize:` throws `InvalidArgumentException`. The old `authorize:`-given construction is unchanged. Migration: add `signatureOnly: true` to keep the old behaviour, or pass `authorize: new AuthorizeOptions(...)`.
- **Breaking** (check name): the core verifier's `counter` check is now `counter_format`, in the verdict `checks` and in its failure reason (`counter_format: missing or not a non-negative safe integer`). Nothing emits `counter` any more.
- **Breaking** (check name): `Authorize::authorize` reports the stateful check as `replay` (set to pass before the claim, flipped to fail when the store refuses it) with the reasons `replay: N is not greater than last seen M (replay)`, `replay: N was already claimed (replay)` and `replay: the replay store failed (fail closed)`. `Authorize::DEFAULT_REQUIRED_CHECKS` is now `counter_format, replay, revocation, plan_root_authorized, audience, validity, grant_ref_bound, operation, params_digest, policy`. A `require` entry `counter` is a documented alias of `replay`.
- **Breaking** (reason text): when an envelope predicate covers the action's verb and resource but a `where` limit is not met, `Predicates::evaluatePredicates` (and the `policy:` reason of `authorize`) names the limit, for example `amount <= 100 not satisfied for payments.send on payments/acme`, instead of `no predicate permits ...`. The text is identical to the TypeScript reference (`test-data/limit-reasons.json`); `no predicate permits <verb> on <resource>` and `envelope grants no predicates` are unchanged for the other cases.

- Add (0.5, additive): `Authorize::authorize` (the full decision: operation binding, predicates, root and delegated caveats, revocation, plan, atomic replay claim; fail closed on any missing component), `Authorize::isAuthorizedFor`, `MemoryStateStore` and `PdoStateStore` (SQLite / PostgreSQL), and the opt-in `authorize:` option of `PcaMiddleware`. Parity with the shared `authorize-fixtures` (31 cases). Defaults unchanged.

- Fix (0.4.2, TS differential): `intentV2Active` now also returns true for a PRESENT but malformed v2 context (e.g. `policy.session.require: "yes"`), as documented ("true iff any v2 check would be reported"): `decideIntentV2` reports failing checks for that context, so a host gating v2 enforcement on the helper used to skip it (fail open). The shared `k042-intentv2-cases` oracle was regenerated from the fixed reference.
- Refactor (no behaviour change): `IntentV2` (3800 lines) is split into the class plus four traits (`IntentV2Schema`, `IntentV2Session`, `IntentV2Acc`, `IntentV2Map`) so the mutation run is sharded per file. Public API unchanged.
- Fix (0.4.2, TS differential, session revocation): the `intent_revocation` primitive passed an input `scope` to `checkSessionRevocation`; the conformance contract (README, reference generator) checks against the default scope `"pca-intent-session:" + session` and only strips `scope` from the evidence. And the text of an array / object value in a reason (`'<id>' is revoked`) was PHP's type name (`array`) instead of ECMAScript `String(value)` (`a,b` / `[object Object]`). New differential kill tests against the shared TS oracles `k042-predjs`, `k042-actionschema`, `k042-intentacc`, `k042-sessrevoc-cases` (no other disagreement).
- Fix (0.4.2, TS differential): `decideIntentV2` passed the PCActn's raw `action.verb` / `action.resource` / `aud` (or the absent marker) into the layer ceilings, the schema conformance, the canonical projection and the W-B input where the reference uses `String(...)` (absent => "undefined"). A PCActn without `action.resource` then failed `layers` ("outside the org ceiling") where TS passes. New `IntentV2DifferentialKillTest` runs the shared `k042-intentv2-cases` oracle; every case agrees (a JSON-null v2 context has no separate PHP spelling: null = none, documented).

- Security / Breaking (0.4.2, R3-01): a pure post-quantum or hybrid Intent Layer v2 session root verifies only under the VERIFIER's pin for its signer, the new verifier-context member `session.pq_pins` (`{<ed25519 key>: <pq_pk>}`), never under the root's own `principals[].pq_pk`. ## 0.4.1 - 2026-10-12

- Security (policy layer): caveats on the root grant outside the envelope are now evaluated like delegated caveats; new policy_caveats/evaluate_caveats helpers (incl. max_spend). The core verifier still does not evaluate caveats. PHP API: `Pca::policyCaveats($grant, $chain)` and `Pca::evaluateCaveats($caveats, $ctx)` (returns `['ok' => bool, 'failed' => list<string>]`; total, fail-closed on unknown types; `max_spend`, `expires`, `not_before`, `rate`, `max_blast_radius`, `reversibility_max`, `delegation_depth`, `budget_alloc`). `Pca::verifyJson` / `verifyPcactnCore` and `PcaMiddleware` still do not evaluate caveats: a resource server enforcing a grant's caveats calls `Pca::evaluateCaveats(Pca::policyCaveats($grant, $chain), $ctx)` with its own action params. Corpus: `primitives.caveat_eval` (41, incl. the `r041-root-max-spend-exceeded` / `-within` pair) in `conformance.php` and `tests/R041Test.php`.
- Threshold share signatures are validated per suite at the wire stage (was a fixed 64 bytes): absent `alg` = ed25519 (64-byte `sig`, no `pq_sig`), `ml-dsa-65` (3309-byte `sig`, no `pq_sig`), `hybrid-ed25519-ml-dsa-65` (64-byte `sig` + required 3309-byte `pq_sig`); a non-string / null / unknown `alg` is a wire failure; a share's `pq_pk` is not judged by the wire (the threshold check owns it). A pure ML-DSA-65 share can now be carried. Corpus: 20 `r041-share-*` vectors; the conformance runners skip a vector whose `requires` names a suite this verifier does not implement (`ml-dsa-87`, `slh-dsa-sha2-128f`). The wire reason for a bad share signature is now `threshold.shares[i]: 'sig' is not canonical base64url (N bytes) for alg '...'` (snapshot `test-data/reasons.tsv.gz` regenerated: 13 reason texts change, no verdict changes).
- BREAKING (`PcaMiddleware`): the `PCA-Action` header is strict unpadded base64url of strict UTF-8 (new public `Pca::decodePcaHeader`, null on failure): padding, the standard alphabet (`+`, `/`), whitespace anywhere, length % 4 == 1, non-zero trailing bits and bytes that are not UTF-8 (overlong, surrogate, truncated) are refused with the existing 401 `PCA-Action header is not valid base64url`. The padded spelling was accepted before. A leading BOM is kept (the strict JSON parser refuses it). Corpus: `primitives.pca_header` (27).
- Version: composer.json carries no `version` field (the release version is the git tag); this entry is 0.4.1.

## Unreleased (BREAKING)

- Reason parity: a capability hop whose body the strict profile cannot canonicalise (e.g. a caveat number outside the safe range) is refused with `hop N: malformed body` like the reference, instead of the generic `malformed capability chain: JsonError` backstop.
- ML-DSA discovery: `ATLAS_PCA_LIBCRYPTO` may list several libcrypto paths separated by `PATH_SEPARATOR` (tried in order; a library without ML-DSA is skipped). The redundant OpenSSL version-number gate is gone: the capability probe (building an ML-DSA-65 key) is the test.

- R6-05 follow-up (robustness): `verifyChain` and `caveatLimitExceeded` take ANY JSON value (`mixed`, was `array`): a chain that is not a JSON array is refused as the empty chain like the reference, instead of a `TypeError` escaping. `signerSetHashRaw` returns null (fail-closed, as documented) for a set whose role / key / `pq_pk` strings the strict profile refuses (e.g. a lone surrogate) instead of throwing `JsonError`. Depth: the strict profile and canonical form refuse nesting past 32 (outermost container = 1, as in the reference); the lax loader stops at 512; tests at 31/32/33 and far beyond.

- R6-03/R6-04 (parity): `verifyThresholdShare` validates the WHOLE signer set like the reference: unknown or wrong-case roles, malformed keys, and an empty / null / short / non-canonical `pq_pk` anywhere in the set refuse it; one key per role, one role per key; a duplicate (role, key) entry only with the same `pq_pk`. `share.role` is required. `t` accepts an integral number 1, 2 or 3 (also `1.0`). `signerSetHashRaw` hashes any string set (UTF-8 byte order); key validity is checked by the registry.
- R6-05 (robustness): `verifyChain`, `verifyJson` and `verifyPcactnCore` are total (a malformed input is a verdict, never a `\Throwable`); the per-hop type check mirrors the reference `wellTyped` (string id/issuer/holder/body_digest/sig, optional alg/pq_pk/pq_sig/holder_pq/parent strings, caveats a list of objects with a string `type`). Correctly SIGNED hops with ill-typed caveats, holder or holder_pq were accepted before, and a hop with a numeric `pq_pk` was accepted.
- R6-02 (security): a signer-set role that registers a `pq_pk` now REQUIRES a PQ (pure or hybrid) threshold share; an ed25519-only share for that role is refused, so an Ed25519 break no longer forges a hybrid-registered role (parity with the TypeScript reference). Corpus: `agent-bound-signerset-with-pq-pk` is now `valid:false`; new positive `agent-hybrid-signerset-with-pq-pk`.
- R5-A1 (security): threshold-share verification is now signer-set PINNED, no longer self-vouched. The share must be for the one key the signer set registers for its role, a PQ/hybrid share verifies only under the set's registered `pq_pk` (a differing share `pq_pk` is refused), the share-suite tag is part of the signed bytes (a classical share cannot be relabelled hybrid), and the signer-set hash now includes a registered `pq_pk` (parity with the TypeScript reference). New corpus vectors: `agent-not-in-signer-set`, `agent-bound-signerset-with-pq-pk`, `agent-hybrid-relabel-*`.

- Suite policy defaults documented: no list = no restriction, an empty list refuses everything, and the hosted API defaults to ed25519 + Ed25519 hybrids (README lists the exact list to pass offline).

- R4-01: `Pca::verifyChain` now takes the root's PQ authority from the verifier, exactly like the TypeScript reference (R3-01). Two new trailing arguments, `$pqPins` (`Obj` or `array<string,string>`: root issuer Ed25519 b64u => PQ public key) and `?Obj $trustedRoot` (the verifier's own stored root capability). A non-ed25519 (pure `ml-dsa-65` or hybrid) ROOT hop is accepted only if `$pqPins[root.issuer]` equals the root's `pq_pk`, or `$trustedRoot` is the root itself (same content hash). Otherwise it is refused with `hop 0: root suite '<alg>' needs a PQ key pinned for the root issuer (policy.pqPins) or the verifier's stored grant (policy.trustedRoot); the root's own pq_pk proves nothing about who issued it (R3-01)`. Before, a pure-PQ root signed with the attacker's own ML-DSA key but naming a victim Ed25519 issuer verified. Callers of `verifyChain` on a root they did not load from their own store must now pass `$pqPins`. `verifyPcactnCore` / `verifyJson` are unchanged in behaviour (they pass the grant as `$trustedRoot`). Internally one `resolvePqKey` choke point mints the only key type (`PinnedPq`) that `verifySuite` accepts, so the PQ verify cannot be called with an artifact key.
